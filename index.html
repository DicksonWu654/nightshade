Start locally

Three ways to run a scan

Normal scans use local source and imports. They do not run your contract or require a Compact compiler.

01Release tarball

Install the CLI

Download the v0.1.0 package from GitHub Releases. The packaged native target is Linux x86-64/glibc with Node 22 or 24.

npm install ./nightshade-compact-0.1.0.tgz
./node_modules/.bin/nightshade path/to/contract.compact
02Docker

Scan in a container

Build from the source checkout and mount the project read-only. Include local Compact imports with your source.

docker build --platform linux/amd64 -t nightshade:local .
docker run --platform linux/amd64 --rm --network none \
  -v "$PWD:/project:ro" nightshade:local \
  path/to/contract.compact
03GitHub Action

Bring it into CI

With code-scanning access, the Action scans the caller workspace, uploads SARIF, and preserves the analyzer exit code. Install project dependencies first.

- uses: DicksonWu654/nightshade@v0.1.0
  with:
    path: contracts
    fail-on: medium

What it catches

Checks for Compact's public and private boundaries.

Findings are static observations to review against the application's intended behavior. Some rules need explicit policy configuration.

↗

Privacy and disclosure

Looks for private witness values reaching public ledger writes, raw authentication preimages being published, low-entropy hash disclosures, and predictable commitment randomness.

View publication rules →
◎

Authorization and identity

Reviews spoofable guards, public-key membership checks, ignored validation, and sensitive state writes. Application-specific authorization needs declared policy.

View authorization rules →
▣

Ledger and shielded assets

Checks state transitions and coin or token operations, including duplicate shielded mint patterns and discarded shielded send results.

View shielded rules →
⌁

Control flow and validation

Flags impossible assertions, caller-supplied time boundaries, and review points where a returned security result is left unenforced.

View validation rules →

A real finding

A witness secret crosses into public ledger data.

The shipped example hashes ownerSecret() for an authorization check, then publishes that same raw value. Nightshade reports the source line, path, and why the boundary matters. An intentional reveal can still be valid and needs human review.

How it works

Evidence from source to report.

Analysis is bounded and profile-specific. Gaps remain visible in coverage and diagnostics.

  1. 01 / Parse

    Build an owned model

    Parse Compact roots and imports into an owned representation, then resolve symbols, types, modules, and the call graph.

  2. 02 / Trace

    Follow values and effects

    Data-flow tracks private witness provenance, ledger revisions, guards, and effects across bounded paths and calls.

  3. 03 / Check

    Inspect public boundaries

    Detectors use shared facts to review disclosure, ledger writes, authorization, and application policy.

  4. 04 / Report

    Keep coverage attached

    Findings include source evidence. Unknown effects, unsupported syntax, and exhausted budgets produce diagnostics.

!

Incomplete analysis is never reported as clean. A complete result means the selected, supported analysis finished. It does not prove contract security or that a reported path can execute.

Know the limits

A review aid with visible boundaries.

Nightshade 0.1.0 is experimental. The packaged native build targets Linux x86-64/glibc with Node 22 or 24; other targets need separate validation. Analysis has bounded path and value tracking, incomplete support for some native operations and dynamic calls, and no general cross-transaction or cryptographic proof.

Policy rules require declared application intent. Intentional disclosure can resemble a defect. No release-wide precision or recall estimate has been established. Review findings and gaps alongside a human audit.
